# Upstream error-enum variants

This small locked Rust program generates the committed fixture at
`sava-rpc/src/test/resources/upstream/solana-error-variants.tsv`. It is first-party
defensive conformance testing for the two error enums this client mirrors one
variant at a time. It is not part of the published library, and Gradle never runs
Rust or accesses the network.

The manifest pins `solana-transaction-error` 4.0.0, published from `anza-xyz/solana-sdk`
commit `9d02e6dc`, and `solana-instruction-error` 3.0.0, published from `5bcc7778`, as
each crate's own `.cargo_vcs_info.json` records. Both source trees are unchanged between
those commits and `983858e1`, the clone HEAD the fixture was reviewed against, which the
header records as `solana-sdk-reviewed`.

## What the fixture pins

The oracle is each enum's own `VARIANTS` constant. Its completeness does not follow
from the array's declared length, which only fixes how many elements the literal holds;
upstream proves it with `test_transaction_error_variants_exhaustive` and
`test_instruction_error_variants_exhaustive`, which iterate every variant through
`strum::EnumIter` and assert each is present. Relying on those tests is why nothing here
parses Rust source: the generator iterates the constant and the Java test reads its own
sealed hierarchy by reflection.

Each row carries the variant's name and its shape, taken from the `Debug` rendering of
the array element: a unit variant renders as a bare name, a tuple variant as `Name(..)`,
a struct variant as `Name { .. }`. Shape turns a name list into a check that no payload
is dropped. It is a presence check, not a schema check: the fixture does not carry a
payload's field count, so a two-field payload against a one-field record passes. The
check is deliberately asymmetric:

* **A payload upstream that the Java record does not take is a failure.** The client
  would silently drop data the cluster sent.
* **A payload the Java record keeps after upstream dropped it is allowed when declared**,
  because historical data still carries the old form. `InstructionError::BorshIoError`
  is the standing case: unit upstream since solana-sdk v3, still parsed both ways here.

Sava supplies none of the fixture's bytes, so a name this client invented cannot
satisfy the test by appearing on both sides.

## Regenerating

From this directory:

```sh
cargo run --locked --release -- --write
cargo run --locked --release -- --check
```

`--check` compares generated bytes with the committed TSV. The fixture records the
sha256 of `Cargo.lock`, `Cargo.toml`, `src/main.rs` and `rust-toolchain.toml`, and the
Java test recomputes all four, so editing the generator without regenerating fails the
build. A dependency change requires a deliberate lockfile update, regeneration, and a
matching update to the pinned versions in the test's expected metadata.

## What it caught

`TransactionError::BailOut` and `InstructionError::BailOut`, added upstream on
2026-08-26 in `fc5d108d` and parsed to the `Unknown` catch-all here until 2026-09-19.
