# @solana/kit transaction v1 (SIMD-0385) message vectors

This locked TypeScript program generates the committed fixture at
`sava-core/src/test/resources/tx/kit-v1-message-vectors.tsv`. It is first-party defensive
conformance testing for Sava's transaction v1 builder, signer, and reader against an
implementation Sava's authors did not write; it is not part of the published library, and
Gradle does not run Node, pnpm, or access the network. The consumer is
`sava-core/src/test/java/software/sava/core/tx/KitV1VectorTests.java`.

The oracle is `@solana/kit` 8.0.0 — `createTransactionMessage({ version: 1 })`,
`setTransactionMessageConfig`, `compileTransaction`, `signTransactionMessageWithSigners`,
`getTransactionDecoder`, `getCompiledTransactionMessageDecoder`, and
`decompileTransactionMessage` — with `@solana-program/system` 0.13.0 supplying the transfer
instruction and `@solana-program/memo` 0.13.0 the memo instruction. Every byte in the fixture
is produced by executing kit: the unsigned message, the signed wire, the account order, the
header, the config mask, and the read-back columns. Sava contributes nothing at generation
time.

## Why a second oracle

The sibling `v1-message-vectors` fixture is generated by a Rust program Sava's authors wrote
against `solana-message`. That program is the right oracle for the wire *format* — every
offset and mask value comes from Solana's own Rust — but a misreading of the SIMD that lives
in the way the program is *driven* (which config a builder should emit, what an unset field
means, which bytes are signed) could be shared between that program and Sava's builder and
agree with itself. Kit is the maintained TypeScript implementation, written by different
people from a different reading of the same specification, and it is what browser and Node
clients will actually produce and consume. Agreement with both is stronger evidence than
agreement with either.

Kit is also the builder-side oracle the Rust fixture is not: its rows are messages a client
library compiled from instructions and a config, so Sava's `TxBuilder` can be asked to
reproduce them byte-for-byte from the same inputs, rather than only to read them.

## What the fixture pins

Nine vectors, each a fee-payer-signed System transfer of one lamport plus whatever `extra`
names, compiled with the `config` column and the fixed blockhash. Columns:

| column | content |
|---|---|
| `id` | vector name |
| `config` | `priority_fee:compute_unit_limit:loaded_accounts_data_size_limit:heap_size` as kit was given them, `-` for an absent field, `none` for no config at all |
| `extra` | `none`, `second-signer` (a second transfer signed by the third seeded key), `memo` (a 3000-byte memo), or `memo+ed25519` (a short memo and an account-free Ed25519-precompile instruction with zero signatures) |
| `config_mask` | the `TransactionConfigMask` kit's compiled message reports, decimal |
| `header` | `numSignerAccounts:numReadonlySignerAccounts:numReadonlyNonSignerAccounts` |
| `static_accounts` | kit's compiled account list in kit's order, base58, comma separated |
| `program_ids`, `instruction_data_hex` | one entry per instruction, in instruction order |
| `unsigned_message_hex` | `compileTransaction(...).messageBytes`, the ed25519 signed payload including the `0x81` prefix |
| `signed_wire_hex` | the base64-decoded `getBase64EncodedWireTransaction` of the signed transaction: the message followed by the signature block |
| `signatures_hex` | one 64-byte signature per signer, in signer (static account) order |
| `read_back_version`, `read_back_config` | kit's own decoders applied to `signed_wire_hex` |

* **`a_example_config`** — the SIMD example config (fee 5000, CU limit 20000, data size 64KiB,
  heap 64KiB); every mask bit set, all four ConfigValues present, mask `31`.
* **`b_empty_config`** — no config; mask `0`, no ConfigValues, kit reads back no config.
* **`c_only_cu_limit`**, **`d_only_priority_fee`** — a single u32 field and the single u64
  field, so the two-bit priority-fee pair and its eight-byte value are pinned on their own.
* **`e_explicit_zeros`** — fee, CU limit, and data size explicitly 0, heap unset. Kit keeps the
  three mask bits (`15`) and writes sixteen zero bytes. Sava's builder cannot emit this shape:
  `computeUnitLimit(0)` *clears* the bit. The consumer reads this vector, re-signs it, and pins
  the builder's divergence deliberately; it does not try to rebuild it.
* **`f_two_signers`** — a second writable signer, so the signature block has two slots and the
  header counts two signers.
* **`g_large_memo`** — a 3000-byte payload, so instruction-payload length encoding is exercised
  well past one byte and the wire is over 3KiB.
* **`h_sava_defaults`** — kit asked for exactly what `TxBuilder` serializes when nothing is set
  (CU limit 1_400_000 and data size 64MiB, no fee, no heap). A bare builder must match it.
  This is the external pin on the deliberate default recorded in `AGAVE_SYNC.md`.
* **`i_two_readonly_programs`** — three read-only non-signer programs (System, Memo, Ed25519)
  in one role, which is where kit's and Sava's account orders may legitimately differ; see
  below. The heap size everywhere is 65536, not 32768, so a heap ConfigValue is never the
  runtime minimum an absent bit would already imply.

Three directions are asserted by the consumer. **Build:** `TxBuilder` with the seeded signers
reproduces `unsigned_message_hex` and `signed_wire_hex` byte-for-byte for every vector except
`e` and `i`. **Read:** `TransactionSkeleton.deserializeSkeleton` reports version 1, each
config value, the raw mask, the header, the blockhash, the accounts in kit's order, the
signer keys, and every instruction, for all nine vectors. **Sign:** zeroing kit's signature
block, parsing, and signing with the seeded keys reproduces kit's signatures in kit's slots,
for all nine vectors.

The fourth direction — kit decoding Sava's bytes — was verified once by the spike's
`decode.ts` (kit decoded every builder output as version 1 with the expected config,
instructions, accounts, and signatures). It is not part of Gradle because it needs Node at test
time; the build direction covers it indirectly, since a builder output that is byte-identical
to kit's wire decodes exactly as kit's wire does.

## Same-role account ordering

Both implementations order accounts fee payer first, then writable signers, read-only signers,
writable non-signers, read-only non-signers. Within one role kit sorts by an
`Intl.Collator("en")` comparison over the base58 text (`getAddressComparator` in
`@solana/addresses`), so `i_two_readonly_programs` compiles to `1111…`, `Ed25519…`, `Memo…`.
Sava's `TransactionRecord.LEGACY_META_COMPARATOR` returns 0 for two accounts in the same role,
so their relative order is whatever the builder's `HashMap` yields — for these keys,
`Ed25519…`, `1111…`, `Memo…`. SIMD-0385 does not specify an order, and both messages are valid
and equivalent, so the consumer asserts canonical equivalence for that vector (same header,
same account set with the same roles, same instructions once indexes are resolved, a valid
signature from each signer over Sava's message) and only requires byte equality if the orders
happen to coincide. `g_large_memo`, whose two read-only programs sort the same way on both
sides, is compared byte-for-byte.

## Determinism

The three signers come from fixed 32-byte seeds (`0x01`, `0x02`, `0x03` repeated), the
blockhash is `0x04` repeated, the transfer amount is one lamport, and the memo and precompile
payloads are constants. Regenerating produces a byte-identical fixture on the same Node
version. The fixture records the versions of every dependency, the Node version that ran the
generator, the seeds and derived addresses, and the sha256 of `package.json`,
`pnpm-lock.yaml`, `pnpm-workspace.yaml`, and `gen.ts`; the consumer recomputes those digests
from the committed files, so an edited generator or a re-resolved lockfile fails the Java test
until the fixture and the expected metadata are regenerated together.

The generator refuses to run unless `package.json` pins exactly `@solana/kit` 8.0.0,
`@solana-program/system` 0.13.0, `@solana-program/memo` 0.13.0, and `tsx` 4.23.12, the
lockfile resolves those versions, and the installed packages are those versions. It also
asserts its own expectations of kit — the `0x81` prefix, message-then-signatures framing,
version 1 on read back, the config surviving kit's own round trip, and the explicit-zero mask —
so a kit behaviour change aborts generation rather than silently rewriting the fixture.

`tsx` runs the TypeScript directly; no `typescript` package is needed. `pnpm-workspace.yaml`
declines esbuild's postinstall script (pnpm 11 reads that setting from there, not from
`package.json`), which keeps `pnpm install` non-interactive.

Regenerate or verify from this directory with:

```sh
pnpm install --frozen-lockfile
pnpm exec tsx gen.ts --write
pnpm exec tsx gen.ts --check
```

`--check` regenerates to memory and reports the first differing line against the committed
TSV, exiting non-zero on any difference. The `node` metadata line is provenance: a different
Node version changes that line and nothing else, and is an expected `--check` difference until
the fixture is regenerated and `KitV1VectorTests.EXPECTED_METADATA` is updated. Dependency
changes require a deliberate lockfile update, fixture regeneration, and matching Java
provenance updates.

## IDE and type checking

`@types/node` and `typescript` are devDependencies for `pnpm exec tsc --noEmit` (also
`pnpm run typecheck`) and for IDE language services; generation runs through `tsx`, which
type-checks nothing, so they cannot affect the fixture's bytes — they are still covered by
`package-json-sha256` and `pnpm-lock-sha256` like everything else, and `tsconfig.json` is
hashed as `tsconfig-json-sha256` because `tsx` reads it. `@types/node` is pinned below the
newest release on purpose: this machine's pnpm supply-chain policy (`minimumReleaseAge`)
refuses packages published too recently, so "bump to latest" is not automatically an
improvement here.
